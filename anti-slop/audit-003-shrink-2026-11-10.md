# antislop audit 003: iso shrink reaudit (2026-11-10)

Scope: owner-requested feature ("how did people actually RIP PS2 ISOs?
implement it") — self-audit of the shrink engine, CLI, GUI and docs on
`feat/iso-shrink` before the pull request. Method: full re-read of
`core/isoshrink.cpp` (the ~1000-line new engine) and the GameStream
additions, plus adversarial test cases for every refusal path.

Baseline: clean configure + build of core, CLI, tests and GUI; full
suite green (4 new test functions, ~90 assertions); CLI end-to-end run
on a generated sloppy ISO; GUI dialog verified offscreen (label and
button state dump).

## Design-stage catches (before the first build)

### S1 (HIGH, would corrupt data): copy direction was inverted

The original plan copied overlapping moves BACKWARD (memmove style for
dst < src). That is backwards: memmove copies backward only when
dst > src. For dst <= src a plain forward copy is the safe one — a
write at dst+done can never reach the unread source region at src+done.
Every move in a compacting rewrite goes down (verified per move and
relied on by the planner), so `copyDown()` is a forward chunked copy
and the safety argument is stated in the code comment.

### S2 (MEDIUM, safety logic gap): parallel-source assumption

The in-place proof initially assumed moves are generated in ascending
source order. Multi-extent files with non-adjacent extents break that
ordering. Fix: moves are explicitly sorted by `src` after planning, and
the two invariants are checked pairwise (dst <= src; no shared source
bytes). Overlapping or shared extents — legal in hardlinked images —
are refused instead of guessed at.

## Findings and fixes (from the test runs)

### S3 (HIGH, false refusal): descriptor scan rejected its own output

`scanDescriptors()` errored on any sector after the PVD that was not a
recognized descriptor. An image this tool had already shrunk puts its
root directory right behind the descriptors (no terminator survives a
`writeRipIso`-style source), so shrinking twice failed with "unrecognized
data". Fix: a non-descriptor sector now ends the descriptor set — same
leniency as the existing all-zero case. Joliet SVDs and UDF descriptors
are still refused by magic.

### S4 (HIGH, wrong data read): PVD logical block size decoded as 32-bit LE

The field at PVD offset 128 is 16-bit LE + 16-bit BE; reading four bytes
LE yields 0x00080800 for a normal image, so every real image with the
field set was refused. Fix: proper 16-bit read; an unset (zero) field is
accepted because the repo's own test ISOs and some third-party tools
leave it empty (the engine is 2048-only regardless).

### S5 (MEDIUM, uint64 underflow): shrunk-again games reported 16 EiB of gaps

After a shrink, duplicate and zero copies are already relinked — they
share the canonical's extent, so reclaiming them frees nothing. The
analysis still counted their footprints, making `gapBytes = stream -
final - dup - zero` wrap around. Fix: copies that already share the
anchor's extent are not counted, the subtraction saturates, and a
regression test re-analyzes a shrunk game (expects all-zero categories
and savings 0).

### S6 (MEDIUM, silent inconsistency): a vanished ul.cfg record kept stale parts

If the game's record disappeared between rewrite and ul.cfg update
(`findByIdSerial` miss), the update was silently skipped and the shrink
reported success with a stale `parts` field. Fix: explicit error telling
the user to fix the parts field.

### S7 (LOW, misleading error): verify read failures were reported as tree changes

`walkIso()` swallows a `false` callback return as "early stop, success".
A read failure during verification therefore surfaced later as "the file
tree changed" (the counts no longer matched) — safe but wrong. Fix: an
explicit `readFailed` flag carries the real message out.

### S8 (LOW, test bug): Rock Ridge refusal test patched the wrong offset

The test grew the BIG.DAT record by two bytes at hardcoded offsets,
assuming a 10-character identifier — it is 9, so the 'RR' bytes landed
outside the record and the refusal never triggered. The engine was
right; the test now derives the system-use offset from the record's own
name length.

## Accepted risks (documented, not fixed)

* **No transactionality**: a power cut mid-rewrite corrupts the game.
  The GUI hides the cancel button once the rewrite starts and both
  frontends warn to keep the drive plugged in; users are pointed at
  "Save a backup copy" beforehand. A full transactional design would
  need a second copy of the game on disk, which defeats the feature's
  purpose on full drives.
* **Hardlinked directory aliases**: two directory records for one extent
  are re-pointed correctly, but a path-table entry under the second name
  fails the (parent, name) match and the image is refused. Pathological
  on PS2 discs; refusing is the documented behavior.
* **Analysis runs twice in the CLI/GUI apply path** (report + rewrite
  each hash the game once). Kept for the dry-run report UX; a one-shot
  maintenance operation can afford the extra pass.
